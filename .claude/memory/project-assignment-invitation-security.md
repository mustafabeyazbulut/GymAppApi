# Assignment invitations require the invitee's own confirmation (2026-09-17)

User's explicit ask: "when adding a member/owner/trainer to a company, a verification code must go to the selected person — it can only be added that way, security matters." Before this, [[project-tenant-onboarding-progress]]'s rework already made `CreateCompanyCommand`/`AddStaffMemberCommand` look up an *existing* registered user by phone instead of creating a new one — but they still attached that user to the company **immediately**, with zero consent from the target. A GymAdmin/BranchManager/SuperAdmin who merely knew someone's phone number could unilaterally put them on staff or make them a company's Gym Admin. This closes that gap.

## What changed

- New entity `PendingAssignmentInvitation` (`Core/GymAppApi.Domain/Entities/PendingAssignmentInvitation.cs`) — user-owned like `OtpVerification`/`DeviceToken`/`Notification`, NOT tenant-scoped (in `GymAppApiDbContext.IntentionallyUnscopedEntityTypes`). Holds `TargetUserId`, `CompanyId`, `BranchId`, `Role`, `RequestedByUserId`, `Code`, `ExpiresAt`, `AttemptCount`, `IsUsed`. Migration `20260917185027_AddPendingAssignmentInvitations`.
- `AssignmentInvitationService` (`Core/GymAppApi.Application/Common/Invitations/AssignmentInvitationService.cs`, static, same style as `PendingVerificationCodeService`) — issues/reissues a 6-digit code, 10-minute expiry, 60s cooldown scoped to `(targetUserId, companyId)` (a user CAN have separate live invitations to different companies at once — that's a legitimate multi-company scenario per `TenantResolutionService`'s own comment).
- `CreateCompanyCommandHandler`: Company + Branch are still created immediately (SuperAdmin's own resources, no one else's consent needed for those) — but the GymAdmin `Assignment` is NOT. Instead it issues an invitation and SMS's the code. `CreateCompanyCommand` gained `RequestedByUserId` (set by `CompaniesController` from the JWT `sub`) purely for audit on the invitation row.
- `AddStaffMemberCommandHandler`: same change — issues an invitation instead of creating the `Assignment` directly. `AddStaffMemberCommandResult` dropped `AssignmentId` (nothing is assigned yet).
- New `POST /api/assignments/confirm` (`ConfirmAssignmentInvitationCommand`, `[Authorize]` with no policy — **any** authenticated user can call it, since the confirmer is the invitee, not staff). Looks up the caller's own live invitations by `TargetUserId == JWT sub`, matches the submitted code, creates the real `Assignment` only then. Wrong code burns an attempt against every live invitation for that user (can't know which one was meant); 5 wrong attempts and a `PendingAssignmentInvitation` is dead. Reuses `UserAlreadyAssignedException`/`ForbiddenException` patterns already in `Assignments/Exceptions`; new `InvalidAssignmentInvitationCodeException` (401) for a wrong/expired/exhausted code, same shape as `InvalidResetCodeException`.
- SMS/in-app-notification wording changed from "you were assigned" to "you're about to be assigned, here's your confirmation code" (SMS) / a codeless heads-up (in-app notification + push, via the existing `NotificationDispatcher`) — the code is deliberately SMS-only, never duplicated into the in-app channel.

## Known gap, not yet addressed — ask before touching

`CreateAssignmentCommand` (`POST /api/assignments`, the OLDER endpoint that attaches an existing `UserId` directly, hardcoded `Role = Member`) was **not** touched — it still attaches immediately, no invitation/confirmation step. Same underlying risk (GymAdmin/SuperAdmin unilaterally attaching a known UserId) technically still exists there. Out of scope for this change since the user's own examples (member/patron/antrenör) map onto `CreateCompany`+`AddStaffMember` specifically, not this legacy endpoint — but if it comes up, raise it rather than assuming it should silently get the same treatment.

## Test-harness gotcha discovered while building this (reusable elsewhere)

`Assignment` is `ITenantScoped`. A test's own `scope.ServiceProvider.GetRequiredService<GymAppApiDbContext>()` (from `_factory.Services.CreateScope()`) never goes through `TenantContextMiddleware` (that only runs for real HTTP requests) — its `AmbientTenantContext` stays at fail-closed defaults (`IsSuperAdmin=false, CompanyId=null`), which makes the global query filter hide EVERY real company-scoped `Assignment` row from a direct `db.Assignments.Any(...)`/`.Single(...)` call, even ones that genuinely exist. Fix: `scope.ServiceProvider.GetRequiredService<AmbientTenantContext>().IsSuperAdmin = true;` before reading, in that same scope (mirrors unit tests' `FakeTenantContext { IsSuperAdmin = true }` pattern, e.g. `TenantQueryFilterTests.cs`). An assertion that "looks" like it passed for the right reason may actually be vacuously true because of this — seen firsthand: `Assert.False(db.Assignments.Any(...))` silently passed even when it should have been asserting something real.

Related, separate gotcha: `CustomWebApplicationFactory`'s DB is shared across every test **method** within one test class (`IClassFixture`). A `SeedAsync()` helper that hardcodes a phone/email literal will silently accumulate duplicate rows across test runs in the same class — `IReadRepository.GetAsync` uses `FirstOrDefaultAsync` so the app layer never throws, it just silently matches an arbitrary (possibly wrong, from a different test) row. Only surfaces once a test asserts something ID-specific rather than just an HTTP status code. Fix: generate a unique phone per `SeedAsync()` call (see `AddStaffMemberAuthorizationTests.UniqueCandidatePhone()`) rather than reusing a hardcoded literal for any entity a handler will look up by that value.
