# Multi-role/multi-company + Package module — decisions and roadmap (2026-09-18)

Started from the user's clarification: "Üyeleri bir company'e atamayacağız ama üyelere paket verince otomatik o şirketin bilgilerini görebilecek" (Members won't be assigned to a company via the staff mechanism — giving them a Package is what links them to a company). This grew into a full multi-role/multi-company design session the same day. This file is the master index — **read it first** before starting work in any of the sub-areas below, then follow the `[[...]]` link to that sub-area's own detail file once one exists.

## Core model decision (settled, don't revisit)

- The Member↔Company relationship is **not** an `Assignment` row. It's established when a `PackageAssignment` is created. Giving a Member a package is what grants them visibility into that company — no separate "add member to company" step.
- Self-service registration stays fully open/company-independent (unrelated, never in question — [[feedback-never-remove-registration-pointer]]).
- `AddStaffMemberCommand` permanently excludes `Member` (only `Trainer`/`BranchManager`) — [[project-branch-ownership-flow]] Task 2. Not a gap to close later with the same mechanism.

## Real-world scope: a user can hold MANY simultaneous assignments

`Assignment.assignments` (mobile `MeResult`) already supports a list, and it needs to — a single user routinely holds 2+ roles across companies/branches in real life. Full enumerated catalog of realistic combinations (kept here so it isn't re-derived):

**Single role, single company (baseline):** plain registered Member with no package · Member with active package at Company A · Trainer at one branch · BranchManager of one branch · GymAdmin of a company · SuperAdmin (platform-wide, no company).

**Same company, multiple roles:** Trainer+Member same branch (staff who trains themselves) · BranchManager+Trainer same branch · GymAdmin+Member own company · GymAdmin+Trainer own company · BranchManager+Member same branch.

**Different companies, different roles:** Trainer(A)+Member(B) · GymAdmin(A)+Member(B) · GymAdmin(A)+Trainer(B) · GymAdmin(A)+GymAdmin(B) (owns multiple gym businesses) · BranchManager(A)+BranchManager/Trainer(B) · Trainer(A)+Trainer(B) (freelance, multiple studios) · Member(A)+Member(B) (memberships at two different gyms).

**Same company, multiple branches:** BranchManager of Branch1+Branch2 · Trainer of Branch1+Branch2 · Member with a branch-specific package at Branch1 and a separate one at Branch2 (depends on the Package-scope decision below).

## Business rules — DECIDED (2026-09-18)

- **GymAdmin + BranchManager in the SAME company, same user: BLOCKED.** GymAdmin already covers every branch; a redundant/conflicting BranchManager assignment for that same company must be rejected. Enforce at invitation-issue time (both directions: assigning BranchManager to an existing GymAdmin of that company, and inviting a GymAdmin who already holds a BranchManager assignment there), mirroring the existing `UserAlreadyAssignedException` pattern in `AddStaffMemberCommandHandler`/`InviteGymAdminCommandHandler`. Cross-company combos are unaffected (GymAdmin of A + BranchManager of B is fine).
- **SuperAdmin + any other role/company (including having their own Package somewhere): ALLOWED.** No extra restriction — the data model already permits it, not worth the complexity to block.
- **Package scope decided at the Package TEMPLATE level, not per-assignment.** A GymAdmin/BranchManager creating a Package chooses "tüm şubeler" (company-wide, `BranchId = null`) or "sadece şu şube" (branch-specific, `BranchId` set) when defining it. Every member who receives that package inherits the same scope. Not chosen per PackageAssignment.

## Package module — full real-world scenario catalog (for when the module is actually spec'd)

**Package types/structure:** duration-based membership (monthly/quarterly/yearly) · session-count based (10/20 seans, may also carry an expiry window) · trial package · single-day pass · PT (personal training, tied to one trainer) · group-class package (scoped to specific class types) · combined package (membership+PT+classes) · family/multi-person package (one purchase, several users) · corporate/bulk package · promo/referral package.
**Scope:** company-wide vs single-branch (decided above, chosen per template).
**Lifecycle:** active · expired (kept as history, not deleted) · frozen (MembershipFreeze — extends EndDate by frozen duration) · cancelled early · renewed (continuity tracking to the prior package).
**Content/entitlement gating (see below):** public/no-login · logged-in-but-no-package · any-active-package · specific-tier/specific-package · company-specific content · trainer-specific content (PT students only) · access auto-revoked when package expires/freezes.

## Decomposition and build order (agreed 2026-09-18)

This whole area is too large for one spec/plan. Agreed order, each its own spec → plan → implementation cycle:

1. **Business rules fix (small, backend-only) — DONE (2026-09-18, commit `16fd92e`).** GymAdmin+BranchManager same-company block enforced in `AddStaffMemberCommandHandler`, `InviteGymAdminCommandHandler` (issue-time, both directions) and `ConfirmAssignmentInvitationCommandHandler` (confirm-time, closes the race window between two concurrent invitations). New `ConflictingAssignmentRoleException` (409). Built TDD, 154 unit + 57 integration tests green.
2. **Package core module — DONE (2026-09-18, commits `413eb73`..`fda5896`, 18-task plan `docs/superpowers/plans/2026-09-18-package-core-module.md`).** `Package` (catalog/template: name, description, scope, duration/session-count, an extensible AccessTier-style field for future content-gating, IsActive) + `PackageAssignment` (Member ← Package, dates, status, freeze/cancel) + `PendingPackageAssignmentInvitation`. Assignment requires the **same SMS-confirmation flow as staff invitations** ([[project-assignment-invitation-security]]'s pattern), only **GymAdmin/BranchManager** may give a package (Trainer excluded). `POST /api/packages`, `GET /api/packages[/{id}]`, `PATCH /api/packages/{id}/active`, `POST /api/package-assignments[/confirm|/{id}/freeze|/{id}/unfreeze|/{id}/cancel]`. `GET /api/auth/me` now returns `packageAssignments` — the actual fulfillment of this whole roadmap's original goal. 187 unit + 59 integration tests, all green.
   - **Real bug caught by the full-flow integration test, now fixed — and it RECURRED in step 3 below, so treat this as a standing rule, not a one-off:** `GetMeQueryHandler`'s query was itself tenant-filtered, but a plain Member has zero `Assignment` rows, so their own ambient `CompanyId` (resolved by `TenantResolutionService` purely from `Assignment`) is always `null` — the `ICompanyScoped` filter on `PackageAssignment`/`Company`/`Package` silently hid a Member's own package from themselves. Fixed with `.IgnoreQueryFilters()` on that query (safe: already pinned to `u.Id == request.UserId`, can't leak cross-tenant), same rationale `TenantResolutionService` already uses.
   - **Standing rule going forward:** any handler that (a) is reachable by a caller who might have NO `Assignment` row (a plain Member — check every endpoint's `[Authorize]` vs `[Authorize(Policy = "StaffManagement")]`, not just the "obviously member-facing" ones) and (b) reads an `ICompanyScoped`/`ITenantScoped` entity (`Package`, `PackageAssignment`, `PackageAssignmentPayment`, `Company`, `Branch`, `Assignment`, and anything added to this family later) needs `.IgnoreQueryFilters()` on that read, PROVIDED the handler does its own explicit authorization check afterward (owner-match or staff-scope check) rather than relying on the filter for security. Check **every** entity read in such a handler, not just the first one that throws `NotFoundException` — step 3's payment query had the bug in three separate reads (PackageAssignment, Package, PackageAssignmentPayment) in the same handler, not just one.
   - **Also fixed along the way:** `PendingPackageAssignmentInvitation` originally had a required FK navigation to `Package` (which is tenant-filtered) while itself being intentionally unscoped — same EF "required end of a filtered relationship" class of bug as above, caught via an EF startup warning before it ever reached a test. Fixed by dropping the navigation, keeping a plain `PackageId` int (matches `PendingAssignmentInvitation`'s existing `CompanyId`/`BranchId`-as-plain-ints precedent). Also: `.gitignore`'s standard NuGet `**/[Pp]ackages/*` rule was silently swallowing the new `Features/Packages/` source and test folders — needed a targeted negation.
3. **Payment/installment tracking — DONE (2026-09-18, commit `10106d2`, spec `docs/superpowers/specs/2026-09-18-package-payment-tracking-design.md`).** `PackageAssignmentPayment` (amount, method, paidAt, recordedBy, note) — `POST/GET /api/package-assignments/{id}/payments`. Overpayment beyond `Package.Price` rejected (409). GET is Member-accessible (their own payments) in addition to GymAdmin/BranchManager/SuperAdmin. **Same `IgnoreQueryFilters` bug as GetMe found and fixed AGAIN here** (3 separate reads this time: PackageAssignment, Package, PackageAssignmentPayment) — see the reusable-lesson note under step 2 below; this is now a confirmed *recurring* class of bug, not a one-off. 196 unit + 61 integration tests, all green.
4. **Reservation + Check-in — DONE (2026-09-18, commit `1bd6b3e`, spec `docs/superpowers/specs/2026-09-18-reservation-checkin-design.md`).** Grew mid-design: a PT/trainer check-in needs to be tied to an advance booking, so this step became two linked entities. `Reservation` (Member/staff books a Trainer+time slot against a SessionBased `PackageAssignment`; conflict-checked per trainer+time; cancel/no-show/check-in lifecycle; a QrCode for scan-or-manual-code check-in) + `CheckIn` (the actual attendance ledger - both reservation-fulfilling and walk-in/no-reservation entries land here). `POST/GET /api/reservations/...` (`ReservationsController`, `[Authorize]` not StaffManagement - Member/Trainer are both legitimate non-staff callers here, gated by each handler's own check) + `POST/GET /api/package-assignments/{id}/check-in[s]` (walk-in, StaffManagement-only - no Trainer/Member self-service) + `POST/GET /api/package-assignments/{id}/reservations`. Check-in decrements `PackageAssignment.RemainingSessions` (both paths); Duration-type assignments record a `CheckIn` but never decrement (nothing to decrement - `RemainingSessions` stays null for them). 232 unit + 64 integration tests, all green.
   - **The same IgnoreQueryFilters bug (see step 2's note) recurred TWICE more while building this, once as a genuinely NEW latent bug from Step 2 itself:** `ConfirmPackageAssignmentCommandHandler`'s `Package` fetch (silently `null`, so every confirmed SessionBased assignment got `RemainingSessions = null` regardless of the package's real `SessionCount` - dormant since Step 2 because nothing checked `RemainingSessions` downstream until Reservation eligibility did) and its already-assigned duplicate check, plus `CreateReservationCommandHandler`'s trainer/time conflict check (silently allowed double-booking). **New standing sub-rule:** `IReadRepository<T>.AnyAsync` has **no** `IgnoreQueryFilters` escape hatch at all (unlike `GetAsync`/`GetAllAsync`, which accept it via their `include` delegate's `IQueryable<T>`) - any `AnyAsync` check whose result must reflect data outside the caller's own ambient tenant scope (a Member's own rows, or any check that must not be blind to another tenant's existing row) must be rewritten as `GetAllAsync(...).Count > 0` instead, not left as `AnyAsync`. Audited every `GetReadRepository<X>().[GetAsync|GetAllAsync|AnyAsync]` call across both the Packages and Reservations features after this was found - all Member-reachable ones are fixed; staff/Trainer-only ones were deliberately left alone (same latent multi-company-staff limitation `TenantResolutionService`'s own "picks the FIRST assignment" comment already documents, not a new regression).
5. **Mobile: multi-assignment/multi-company awareness + context switcher** (the original "Parça 3") — **Member-facing side DONE (2026-09-18/19, two sessions).** Full status/decisions live in GymApp's own memory (`project-membership-real-data-status.md`, per [[feedback-never-remove-registration-pointer]]'s sibling rule that mobile memory stays in the GymApp repo) — read that file before resuming this step. Short version: Membership, Home AND Classes screens are now all wired to real data (`PackageAssignment`/`Reservation`/`CheckIn`), sharing one "which membership am I viewing" context + switcher across all three. `MeResult.staffAssignments` (list) exists for the drawer. **Real product-model finding, not just a repository swap:** the mock "Classes" screen (shared, capacity-limited class schedule, BJJ/Fitness categories) has NO backend equivalent - the actual model is a 1-on-1 Trainer reservation (`trainerId` + `scheduledAt`, no group/capacity concept at all). Mobile's Classes screen was redesigned around the real model (list own reservations, book one by picking a trainer + date/time). **New backend endpoint added to support this: `GET /api/package-assignments/{id}/trainers`** (commit `534b181`) - there was no way at all to discover which Trainer ids are valid for `CreateReservationCommand.TrainerId`, this was a hard blocker for a real "book a session" flow, not optional polish. **New backend gap discovered, not fixed:** there is no Member self-service freeze - `FreezePackageAssignmentCommand`/Unfreeze/Cancel are all `StaffManagement`-only (see `PackageAssignmentsController`), so the mobile freeze/renew buttons were removed rather than left as dead/lying UI. If a self-service freeze is ever wanted, that's a new backend design decision (who can request it, does it need staff approval), not a mobile-only fix. **Still open:** Progress screen is still mock data (not touched either session). **Also still open, unchanged:** the multi-company *staff* context switcher (letting a GymAdmin of 2+ companies pick which one "Add Staff Member" targets) needs `TenantResolutionService` to stop "always pick the first Assignment" and accept an explicit caller-selected company - a cross-cutting backend change (`ITenantContext`/`TenantContextMiddleware`/every `StaffManagement` endpoint), deliberately not attempted as out of scope for an unsupervised pass.
   - **Mistake made and corrected the first session, worth remembering:** committed the dev-only CORS block in `Program.cs` (commit `236b7df`) despite [[project-tenant-onboarding-progress]] explicitly documenting it must always stay uncommitted/local-only (it was accidentally committed once before, commit `135b67a`, and reverted for exactly this reason). Caught later in the same session by actually reading that memory file before touching `Program.cs` again - reverted (`736b92b`) and the block was manually re-added to the working tree WITHOUT re-committing. **Lesson: read a file's own project memory before assuming an existing uncommitted diff is "leftover work to finish" - it may be there ON PURPOSE.**
   - **Live end-to-end verification NOT completed either session** - blocked by a genuine environment issue, not a code bug: this sandbox's local Docker Postgres (`gymapp_dev` on `localhost:5432`) is reachable instantly via `docker exec ... psql` and via `Test-NetConnection` from PowerShell, but every real .NET/Npgsql connection attempt from `dotnet run` (tried via both Bash and PowerShell launchers) times out (`Npgsql.NpgsqlException: The operation has timed out`) - confirmed hitting the *correct* `gymapp_dev`/`tcp://localhost:5432` in the error message, so it's not a wrong-target mystery, just a hung TCP handshake specific to the .NET process in this sandbox (IPv6-vs-IPv4 resolution mismatch is the leading suspect, not confirmed). Also separately noticed: `gymapp_dev`'s `__EFMigrationsHistory` is stuck at only 6 migrations (through `20260916110343_AddUserIsAccountFrozen`) - missing every Packages/Reservations/Notifications/PendingAssignmentInvitations-era migration, i.e. this specific Docker volume hasn't actually been migrated forward since 2026-09-16, despite plenty of memory entries describing later features as "verified against real Postgres" (those verifications happened in different sessions/environments). **If resuming: don't assume this Docker Postgres is a quick fix - budget real time for either fixing the Npgsql connectivity or standing up a fresh dev DB, and run `dotnet ef database update` (confirm it actually reports "Applying migration '...'" lines, don't trust a silent exit 0 alone) before trusting any live-against-Postgres claim.** Verification this round rested entirely on the automated suites: 236/236 backend unit tests, 89/89 mobile tests, `flutter analyze` clean.
6. **Video/content library** — explicitly deferred to a fully separate future plan (own spec). The only thing carried into step 2 for forward-compatibility is the AccessTier-style field on `Package`; the actual content system (upload/storage/playback, admin content management, entitlement checks against tier) is out of scope until then.

- **Progress screen — DONE**, rebuilt on a real `ProgressNote` entity (trainer-entered technique/condition scores 0-100 + free text) recorded via a Trainer's own schedule screen; attendance/classesThisMonth stay computed client-side from real CheckIns (never trainer-entered, to avoid two data sources drifting apart).

- **POST /api/assignments (staff invite) — was creating an Assignment directly, now goes through the same SMS-confirm invitation flow as everything else** (`PendingAssignmentInvitation`).
- **Self-service Freeze/Unfreeze — DONE** (backend: `PackageAssignmentsController`'s Freeze/Unfreeze changed from StaffManagement-only to `[Authorize]` + owner-or-staff check in the handler; mobile: a freeze/unfreeze button on MembershipScreen). Cancel deliberately stays staff-only (irreversible).

New `ConfirmInvitationScreen`, reachable from the drawer by anyone.
- **Package Management mobile UI — DONE.** `GET /api/package-assignments` (new query, `GetPackageAssignmentsQueryHandler` - staff-facing list scoped by ambient CompanyId same as `GetPackagesQueryHandler`, optional `memberPhone` filter, per-assignment totalPaid/remainingBalance) was the one new backend piece needed - `RecordPackageAssignmentPaymentCommand` already existed but had no way for staff to discover a target `PackageAssignmentId`. New mobile `package_management` feature: package template list/create/activate-toggle, Assign Package (SMS-confirm invite, same pattern as CreatePackageAssignment), Assignments+Payments screen (search by member phone, record Cash/Card/BankTransfer payment from a bottom sheet).
- Also fixed two confirmed, pre-existing mobile/backend contract drift bugs found by reading code (not reported): `CreateCompanyScreen`/`AddStaffMemberScreen` were sending fields (`branchName`, `branchAddress`, `gymAdminFullName`, `gymAdminEmail`, staff `fullName`/`email`) the backend commands had already stopped accepting - silently ignored by model binding, so users filled in meaningless fields; and their success messages described the wrong ("Forgot Password") flow.

Still open (not yet started, real remaining gaps for a "complete Phase 1"): mobile UI for `InviteGymAdmin` (`POST /api/assignments/gym-admin` exists, zero mobile screen - SuperAdmin-only flow); `GET /api/branches` returns silently empty for a Member with no Assignment row (minor, no current mobile screen exposes it to a Member so low priority). Step 6 (video/content library) not started, not designed.
